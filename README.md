# Infra Lab — интерактивная сетевая лаборатория

Запуск: `npm start` (или `node server.mjs`) из каталога проекта, затем открыть http://127.0.0.1:4178. Нужен Node.js 22+; установка зависимостей не требуется. Проверки: `node --test tests/*.test.mjs`.

Правая кнопка на холсте создаёт стойку, клиента или сетевое устройство; на объекте предлагает допустимые дочерние объекты и новый сетевой интерфейс. Заголовки перетаскиваются, стрелка сворачивает вложенность. Соседи одного уровня не пересекаются: перетаскивание останавливается перед препятствием; при создании, росте и раскрытии контейнера пересекающиеся соседи сдвигаются вниз. Положение относительно родителя сохраняется. Контакты соединяются двумя кликами или перетаскиванием площадки контакта, один внешний кабель на интерфейс. Для удаления кабеля используйте правую кнопку на линии или кнопку в свойствах интерфейса. Нажатие на кабель или занятый порт показывает его концы в свойствах. При сворачивании на границу родителя выводятся только внешние подключения, внутренние связи сохраняются.

Колесо мыши масштабирует холст вокруг курсора (20–200%). Кнопки +/− изменяют масштаб вокруг центра; нажатие на процент возвращает 100%. «Вписать» учитывает ширину и высоту всей схемы. Клавиши +/− и 0 делают то же самое. Shift + колесо прокручивает горизонтально. Пробел + левая кнопка или средняя кнопка мыши сдвигают холст. Положение камеры сохраняется отдельно от схемы. ↶ / Ctrl+Z отменяет до 30 последних изменений в текущей сессии.

Кнопка «?» на каждом узле и карточка в свойствах объясняют его назначение, сетевое поведение и пример применения. Интерфейсы создаются только у поддерживающих их сущностей. Типизация учитывает физические NIC, виртуальные адаптеры, veth, SFP и среды передачи. У стойки, Docker Engine, containerd и kubelet собственных сетевых интерфейсов нет; управление runtime показано отдельно от сетевых кабелей.

Демо: клиент → SW-01 access VLAN 10 → оптический trunk (SFP+ LR, SMF) → ODF → SW-02 access 10 → физический `eno1` сервера → мост Proxmox `vmbr0` → `net0 / virtio` ВМ → `eth0` Ubuntu → публикация `:8080` в ядре Ubuntu → Linux-мост `br-app` → хостовый конец `veth101` → парный `eth0` контейнера → Nginx `:80`. Мост Proxmox явно объединяет физический NIC и vNIC ВМ; отдельный линк «Адаптер ВМ ↔ гостевая ОС» показывает один адаптер в двух представлениях. Внешний IP Ubuntu — `10.10.0.10`, IP шлюза контейнеров `172.18.0.1` назначен самому мосту `br-app` в ядре Ubuntu; у контейнера — `172.18.0.2`. Docker Engine управляет сетью, но собственного промежуточного NIC в пути нет. Публикация перенаправляет `10.10.0.10:8080` на `172.18.0.2:80`. Простое размещение внутри объекта сеть не создаёт.

Проверка сайта запускает визуальную трассировку: DNS-запрос и ответ, HTTP-запрос, публикация/DNAT, запрос к контейнеру, ответ контейнера, обратная трансляция и HTTP-ответ клиенту. Жёлтый маркер проходит порты и линки; пройденное подсвечивается зелёным. Внутренние переходы коммутатора/маршрутизатора показаны временной линией и не создают кабель. Пауза, предыдущий/следующий шаг, ползунок, 0,5×…4×, повтор, «До конца», «Найти» и «Сбросить» находятся над холстом. По строке журнала можно перейти к соответствующему шагу. При ошибке красным отмечаются устройство, контакты и, когда известен, неисправный линк; рядом указана причина. Изменение сетевой конфигурации сбрасывает устаревшую трассу, перемещение/сворачивание сохраняет её.

Если полностью разорванный граф не задаёт следующий выходной порт, симулятор сообщает об отсутствии объявленного пути у отправителя, а не придумывает место обрыва. При известном пути ошибки VLAN, физического канала, LAG и фильтрации привязаны к конкретному переходу.

Порты свитча явно показывают ACCESS/TRUNK, VLAN/native VLAN и группу LAG/bond. Кнопка «Цвета VLAN» включает цветовые полосы на портах и разметку кабелей; trunk нескольких VLAN показан многоцветным. Легенда цветов расположена под тулбаром. Режим запоминается локально. LAG настраивается у интерфейсов общим именем группы; поддержаны static, LACP active/passive и абстракция bond active-backup. Несогласованный LACP, разные VLAN внутри группы и несовместимые скорости блокируют передачу. Passive/passive не согласуется; active/passive и active/active согласуются. Для active-backup используется один рабочий участник, резерв переключается при отключении основного. В модели нет таймеров LACP, распределения потоков по хешу, оценки суммарной пропускной способности и MLAG; отдельный kernel-интерфейс bond не создаётся автоматически.

Физические контакты квадратные с меткой «ФИЗ», виртуальные — круглые пунктирные с меткой «ВИРТ». Легенда над холстом объясняет кабели, виртуальные соединения, veth, адаптер ВМ и принадлежность мосту. Нажатие на кабель показывает оба конца, тип интерфейсов и объяснение смысла связи. Каналы двунаправленные; пересечения и изгибы линий не создают соединений.

Лассо: протяните левой кнопкой по свободному месту. Выбираются полностью попавшие в рамку объекты; если выбран родитель, вложенные объекты не дублируются в группе. Shift/Control дополняют выделение, Shift/Control + клик по заголовку переключают отдельный объект. Esc снимает выделение. Перетаскивайте группу за заголовок любой выбранной ноды; взаимные расстояния и коллизии сохраняются. Свойства группы предлагают удаление с подтверждением и возможностью отмены.

Пассивные панели обозначены парами `PORT 1 IN ↔ PORT 1 OUT`, `PORT 2 IN ↔ PORT 2 OUT` и т. д. IN/OUT — стороны панели, не однонаправленный канал. Кнопка добавления на панели создаёт сразу пару, с соответствующим пассивным профилем среды. Каждая пара независима. Контекстное меню закрывается после удаления кабеля, по Esc и по клику вне меню.

Откройте раскрывающуюся подсказку над холстом и нажмите «Проверить сайт site.lab:8080». Учебный браузер клиента покажет ответ сайта и подробный путь по фактически связанным интерфейсам, включая access/trunk, оптическую панель, физический NIC, vmbr0 и virtio. Этот просмотр не запускает настоящий nginx. Перед загрузкой демо сохраняется предыдущая схема; кнопка «До демо» возвращает её. Кроме того, работает экспорт JSON и отмена изменений.

Docker Engine управляет контейнерами и сетями, но не объединяет свои интерфейсы автоматически. Программный мост создаётся отдельно внутри Proxmox, ОС или Docker. Как у программного свитча, его порты входят в один L2-сегмент. В свойствах моста раздел «Участники» позволяет присоединить интерфейсы локального хоста и его гостей, сохранив внешние кабели этих адаптеров. Сиреневый пунктир — внутренняя привязка; зелёная линия — кабель. Один интерфейс может принадлежать только одному мосту. Область ограничена хостом и его гостями, произвольное объединение адаптеров удалённого хоста не допускается. Бридж не выполняет маршрутизацию или DHCP. В реальной ОС сетевую конфигурацию участника обычно переносят на логический интерфейс моста; прототип не исполняет сетевые команды ОС.

«DHCP» выдаёт адреса автоматическим интерфейсам только в сегментах с одним включённым сервером. Пул задаётся как смещения хостов от адреса сети; ручные IP, адрес шлюза и DNS резервируются. «Авто IP» дополнительно действует как учебный планировщик для сегментов без DHCP: использует существующую подсеть или выбирает свободную `10.42.N.0/24`. Это не протокол DHCP. Изменение IP/префикса/шлюза/DNS вручную переключает интерфейс в ручной режим.

Модель явно хранит устройства, родительскую вложенность, интерфейсы IPv4, внешние кабели, внутреннее членство в мостах, назначенные подсети и службы. Коммутатор и виртуальный мост объединяют свои порты на L2. Маршрутизатор и фаервол пересылают трафик между непосредственно подключёнными подсетями с проверкой шлюзов и обратного пути. Можно задать следующий шлюз на выходном интерфейсе для транзита. Фаервол запрещает ICMP или перечисленные TCP-порты при транзите; прочий трафик разрешён. DNS — доступный по сети сервер со статическими A-записями. HTTP — учебная служба контейнера с отдельным правилом публикации. Проверка отказывается работать при конфликтах и ошибках IP во всей схеме.

Автосохранение в localStorage браузера, JSON экспорт/импорт (`version: 1`, `schemaVersion: 2`), восстановление демо через встроенный диалог. Старые схемы переносятся автоматически: порты прежней сущности Docker bridge переходят отдельному дочернему мосту, их ID, IP и кабели сохраняются; существующие контейнеры остаются в Docker Engine. Перед переносом текущего localStorage сохраняется копия в `infra-lab-backup-before-engine-v2`. Схема не отправляется наружу. HTTP-сервер слушает исключительно `127.0.0.1`. Реальные ВМ, контейнеры и пакеты не создаются; настройки ОС не меняются.

Кабели прокладываются ортогонально с обходом посторонних нод и заголовков родительских контейнеров. Контакты расположены на границах нод, толщина линий не зависит от зума. При тесной расстановке прокладчик уменьшает зазор; если обойти препятствия не удалось, кабель обозначается оранжевым пунктиром и выводится подсказка раздвинуть ноды. Визуальные пересечения линий не являются соединениями. Общая оптимизация пересечений и ручные промежуточные точки маршрута пока отсутствуют.

Физический каталог: RJ45 10/100/1000 и 10G, SFP SX/LX/BX-U/BX-D/1000BASE-T, SFP+ SR/LR/DAC, пустой SFP-слот, BNC 50 Ω 10BASE2, F 75 Ω MoCA. Профиль задаёт разъём и модуль в свойствах интерфейса. При соединении подбирается общая среда; несовместимые новые подключения отклоняются. У кабеля можно изменить среду и длину в свойствах. Несовместимость среды, скорости, TX/RX BiDi и дальности отображается в диагностике и прекращает симуляцию. Оптика показана голубым, коаксиал — жёлтым, привязки мостов — сиреневым пунктиром. Старые схемы сохраняют абстрактные кабели без проверки среды, чтобы обновление не разрушало их; для физической проверки выберите конкретные профили и среду.

Свитчи поддерживают access VLAN и trunk с allowed/native VLAN, NIC — необязательный тег 802.1Q. VLAN ограничены 1–4094, до 128 значений в списке trunk. Untagged-кадры при переходе в access-порт относятся к его VLAN; на выходе access тег отсутствует. Native VLAN trunk передаётся без тега. Локальный PVID программного моста может отличаться от номера VLAN внешнего свитча: после access-порта трафик идёт без тега, это отмечается в пути.

Устройства перехода: медиаконвертер RJ45↔SFP, MoCA-адаптер, BNC-повторитель 10BASE2, Ethernet-концентратор, медная патч-панель и ODF. Медиаконвертер прозрачен для VLAN и требует совместимой скорости двух портов. Пассивные панели соединяют только пары 0↔1, 2↔3; проверяются активные концы и суммарная длина через панель. Это расширяемый каталог распространённых устройств, не полный каталог всего оборудования.

Ограничения: до 400 объектов при импорте; IPv4 /1…/30, без IPv6, STP, обучения/старения MAC, ARP-таймеров, NAT общего назначения, таблиц статических маршрутов и динамических протоколов. Нет временной модели CSMA/CD, PoE, PON/OLT/ONT, DSL, Wi-Fi, модемов DOCSIS, оптического бюджета и реальных пакетов. Дальности оптики — упрощённые пределы: не моделируются классы волокна, сварки, затухание, модальные кондиционеры и матрицы совместимости производителей. Профиль порта описывает выбранное оборудование, а не проверяет возможность физической замены RJ45 на SFP в конкретном шасси. DHCP — мгновенная выдача без таймеров аренды; DNS без кеша/рекурсии. Правила фаервола упрощены, UDP/53 не фильтруется. Управление ориентировано на мышь; сенсорное управление не проверено.

Справочные первоисточники: [Cisco SFP data sheet](https://www.cisco.com/c/en/us/products/collateral/interfaces-modules/gigabit-ethernet-gbic-sfp-modules/datasheet-c78-366584.pdf), [Cisco SFP/SFP+ installation notes](https://www.cisco.com/c/en/us/td/docs/interfaces_modules/transceiver_modules/installation/note/78_15160.html), [Cisco access/trunk](https://www.cisco.com/c/en/us/td/docs/switches/datacenter/nexus5000/sw/layer2/503_n1_1/Cisco_n5k_layer2_config_gd_rel_503_N1_1_chapter6.html), [Docker bridge](https://docs.docker.com/engine/network/drivers/bridge/), [Docker published ports](https://docs.docker.com/engine/network/port-publishing/), [сетевая модель Proxmox](https://github.com/proxmox/pve-docs/blob/master/pve-network.adoc).

Слежение за пакетом: тумблер в верхнем тулбаре плавно приближает текущее устройство на каждом шаге трассы, включая точку ошибки. Выбор сохраняется локально. При выключенном слежении запуск и перемотка сохраняют ручной вид холста. Ручные зум, панорама и кнопка «Вписать» прерывают текущее движение камеры.

ПКМ по контакту или его подписи открывает свойства и удаление интерфейса. Удаление убирает связанные кабели и привязки мостов; ↶ восстанавливает всё одним действием. У ODF и патч-панелей удаляется целая пара IN/OUT; номера оставшихся пар сохраняются. Справка Docker объясняет bridge, veth, маршрутизацию, публикацию/NAT и отличия от host/none/macvlan/ipvlan.


Для опубликованного контейнерного сайта внутри Ubuntu показан отдельный блок сетевого стека: вход eth0:8080, PREROUTING/DNAT на IP контейнера:80, выбор маршрута и FORWARD к Linux-мосту. Янтарный точечный пунктир показывает внутренний путь ядра, не добавляет кабель и не соединяет L2-сегменты. В трассе DNAT, маршрутизация и обратная трансляция conntrack выделены отдельно; камера показывает блок вместе с выходным мостом. При отсутствии bridge membership показан разрыв. Подписи выводятся из текущих настроек интерфейсов и публикации.

Кнопка «IP/порты» показывает заголовок каждого пакета у маркера, в панели шага и журнале. При NAT показаны обе версии с выделением только изменившихся полей. TCP-порт клиента для демо — 49152, DNS/UDP — 53000; эти порты выбраны симулятором, а не прочитаны из реального захвата. На L2-переходах IP и порты не меняются. При DNAT сохраняется источник клиента; ответ контейнера адресован клиенту и получает обратную трансляцию источника на опубликованный адрес хоста. У ICMP транспортных портов нет. До формирования пакета при ошибке конфигурации значения не выдумываются. Переключатель сохраняется локально.

«Логическая сеть» открывает читаемую цепочку из семи этапов без вложенных рамок: физический NIC → vmbr0 → vNIC ВМ / eth0 гостя → ядро Ubuntu → br-app → veth-пара → контейнер. Связи получены из текущей конфигурации; разрывы отмечены. Docker Engine объясняется отдельно как менеджер сети. В этом режиме можно запустить HTTP-проверку по IP хоста, шагать по трассе, видеть активный этап и сравнивать поля NAT. Подробный редактор доступен кнопкой возврата к схеме.

На основном холсте виртуальный интерфейс локальной ОС, включённый в Linux-мост, показан один раз на границе этого моста. Например, veth101 остаётся интерфейсом Ubuntu в модели и свойствах, но нарисован как порт br-app с подписью владельца. Линия принадлежности к мосту заменена видимым внутренним L2-переходом от интерфейса моста к veth. От этого контакта идёт единственная veth-пара к eth0 контейнера. Поэтому путь читается последовательно: внешний eth0 → ядро/DNAT → br-app → veth101 ↔ контейнер. Адрес самого моста отмечен L3; отдельного кабеля или копии интерфейса не создаётся. Сворачивание учитывает этот способ отображения и сохраняет внешний L3-контакт группы.

Маршруты измеряются и рассчитываются в немасштабированных координатах холста. Зум изменяет только отображение, не выбирает новую прокладку кабеля. На поперечных пересечениях горизонтальная линия получает дугу с просветом над вертикальной; это не соединение. Общие контакты, углы и совпадающие участки не считаются поперечным пересечением. Форма дуг задана в координатах схемы и масштабируется вместе с ней. Подсветка, выбор кабеля и маркер пакета следуют той же кривой. Выход блока ядра направлен вниз после FORWARD, без встречного горизонтального участка; маршрутизатор убирает лишние ступени, когда прямой ортогональный обход свободен.

Ручная прокладка: щёлкните линию или занятый контакт. Квадратная ручка перемещает участок поперёк линии, круглая — точку изгиба. Концы остаются на портах; прямые углы сохраняются. При необходимости на прямом участке создаются дополнительные изгибы. «Автопрокладка» возвращает рассчитанный маршрут, «Готово» скрывает ручки. Escape отменяет текущий drag, ↶ отменяет завершённую правку. Прокладки сохраняются в wireRoutes вместе с JSON и локальным состоянием; при общем переносе концов трасса переносится с ними. При свёрнутом объекте используются автоматические прокси, после разворачивания ручной маршрут возвращается. Доступны кабели, привязки мостов и внутренние линии ядра.

Параллельные кабели разведены минимум на 16 единиц холста между осями; при видимой толщине до 3 единиц это оставляет больше трёх толщин чистого зазора. Геометрия и толщина масштабируются вместе, поэтому правило сохраняется при зуме. Автоматическая прокладка учитывает уже проложенные и сохранённые ручные трассы. При ручном наложении участок краснеет; сохранение отклоняется, прежний маршрут остаётся. Поперечное пересечение допускается и оформляется дугой. Чужой изгиб, попавший на середину линии, также не считается сетевым соединением и получает дугу.

Двойной клик по линии добавляет точку маршрута без изменения формы. Точку можно перетащить; ПКМ по круглой ручке открывает «Удалить точку». Удаление локально соединяет соседние участки прямыми углами, сохраняя остальную трассу. Единственный геометрически необходимый изгиб между несоосными контактами можно перемещать; удалить его с сохранением прямых углов нельзя.

ПКМ по свободному месту отменяет активное подключение, перенос точки/участка, перенос объекта, лассо или панораму. Сохранённые связи не затрагиваются. Если активного действия нет, ПКМ открывает обычное меню. Для отмены переноса объекта восстанавливаются также позиции соседей, сдвинутых коллизиями.

Ctrl+C/V копируют и вставляют выделенные объекты с потомками, внутренними кабелями, membership мостов и соответствующими ручными трассами. Создаются новые ID; внешние кабели не дублируются. Ctrl+Z отменяет, Ctrl+Y и Ctrl+Shift+Z повторяют; в тулбаре есть кнопка повтора. Новая правка после отмены очищает ветку повтора. В полях ввода сочетания редактируют текст стандартным способом.

Внутренний линк ограничен ближайшей общей родительской нодой. Например, net0 ВМ → eth0 Ubuntu прокладывается внутри ВМ; граница контакта направляет начальный участок внутрь. Автоматический обход и дуги не выходят за пределы родителя, ручной выход отклоняется. Если прежняя ручная трасса перестала помещаться, отображается ограниченная автоматическая прокладка, сохранённая трасса остаётся доступной. В блоке ядра Ubuntu вход идёт снаружи карточки слева, а маршрут занимает отдельную нижнюю полосу под текстом.

Создание интерфейсов типизировано общей политикой модели и UI. У ВМ появляются netN/виртуальные NIC, у контейнера ethN/виртуальные NIC, у гостевой ОС виртуальный ethN, у ОС на физическом сервере физический enoN. Для Linux доступно отдельное создание vethN. Свитч, маршрутизатор и физический сервер получают физические разъёмы; ODF и патч-панель — согласованные пассивные пары; медиаконвертер, MoCA и коаксиальный повторитель имеют только соответствующие два разъёма. Docker Engine и стойка не получают собственных NIC. У Linux-моста создаётся один brN/vmbrN, затем добавляются участники. Номера выбираются без конфликтов имён. Недопустимые типы/профили в редакторе отключены; прежние сохранённые интерфейсы не удаляются автоматически.

CAD-рамка слева направо выделяет только целиком попавшие объекты; справа налево — задетые рамкой, включая касание границы. Рамка окна синяя сплошная, рамка пересечения зелёная пунктирная; режим подписан во время жеста. Shift добавляет к выделению. Внутри большого контейнера рамка выбирает его детей, а не всю стойку только из-за вложенности.

Привязки мостов используют тот же ограниченный маршрутизатор: например, фиолетовая связь eno1 → vmbr0 остаётся внутри SRV-01. Сохранённые ручные трассы дополнительно проверяются на пересечение посторонних нод. При перемещении устройства на такую трассу отображается безопасная автоматическая прокладка, а сохранённые точки остаются в проекте. Ручное сохранение линии сквозь устройство отклоняется.



## Приложения, контейнеры и кластеры

Приложение создаётся внутри Ubuntu, Debian, Windows Server, Docker контейнера, контейнера Pod и непосредственно на Linux-хосте Proxmox. ВМ и сервер требуют сначала ОС. Приложение использует NIC среды, собственного адаптера и кабеля нет. У HTTP-приложения задаются команда, TCP-порт и включение службы. В модели HTTP слушает на адресах среды; конфликт двух включённых приложений на одном порту общего namespace диагностируется.

Docker Engine → Docker контейнер → Приложение. Контейнер хранит образ, состояние, команду, restart policy, CPU, память, environment и volumes; NIC и правило публикации находятся у контейнера. Внешний порт хоста и целевой порт приложения задаются независимо. Пока реализована одна публикация TCP и явная bridge-сеть. CPU, память, тома, environment, образ и restart policy — сохраняемые параметры схемы; реальные процессы и ограничения ресурсов не запускаются. Остановка контейнера/приложения учитывается при проверке HTTP.

Старый «Контейнер-сайт» автоматически становится Docker контейнером с дочерним приложением. ID контейнера, NIC, IP, кабели, публикация и ручные маршруты сохраняются. Резервная копия исходного localStorage создаётся один раз под ключом infra-lab-backup-before-applications. Удаление приложения не создаёт его заново.

Kubernetes: ОС → Узел Kubernetes (worker/control-plane, CRI runtime, CNI, Pod CIDR) → Pod → Контейнер Pod → Приложение. На Windows доступен worker. Контейнеры Pod используют общий IP/NIC Pod, независимые NIC у них запрещены. Namespace и labels сохраняются; состояние Pod учитывается для HTTP. CNI/overlay, Service, Ingress, scheduler и etcd не эмулируются, сетевые подключения Pod задаются явно.

Через верхнее «Добавить устройство» создаются Кластер Proxmox и Кластер Kubernetes. У Proxmox VE / Узла Kubernetes выберите кластер в свойствах. Штрихпунктирные подписанные связи объединяют участников, видны при сворачивании и не создают сетевую связность. Группа кластера не перемещает физические серверы внутрь себя. Удаление группы очищает членство, участники остаются. При копировании членство сохраняется, а при копировании вместе с группой переназначается на её копию. Импорт/экспорт и история сохраняют структуру и параметры.


## Демосхема Proxmox + Kubernetes

Кнопка «Демо кластеров» загружает 38 сущностей (включая kubelet и containerd): 3 физических Proxmox-хоста (адреса управления 10.10.0.11–13 на vmbr0), 3 ВМ (control-plane 10.10.0.20, worker-01 .21 и worker-02 .22), два Pod с Nginx, клиент, DNS, коммутатор и две логические группы кластеров. ВМ control-plane и worker-02 изначально свёрнуты, главный путь worker-01 раскрыт. Исходная схема сохраняется в «До демо»; повторная загрузка этого же демо не затирает исходную копию.

В инструкции над холстом нажмите «Проверить сайт site.lab:30080». Это учебный браузер в симуляторе: HTTP 200 подтверждает прямой и обратный путь модели. DNS возвращает 10.10.0.21. Service nginx-web (namespace demo, selector app=nginx, NodePort 30080, targetPort 80, externalTrafficPolicy Local) выбирает готовый локальный Pod. kube-proxy представлен явным правилом ядра ВМ: DNAT 10.10.0.21:30080 → 10.244.1.10:80; source IP клиента сохраняется. cni0 → хостовый veth ↔ eth0 Pod → общий namespace → контейнер containerd → приложение Nginx. Ответ проходит обратную трансляцию conntrack.

worker2.lab:30080 обращается ко второй реплике 10.244.2.10:80 на worker-02. Запрос к control-plane:30080 останавливается из-за отсутствия локального готового endpoint (политика Local). Изменения namespace, selector, состояния Pod/приложения и сетевой связности учитываются. Сетевые интерфейсы контейнера не дублируются: они принадлежат Pod. Реальные контейнеры, etcd, Corosync, CNI overlay, scheduler, ClusterIP и Ingress не запускаются и не эмулируются. Реализован явный TCP NodePort Local с локальным backend, а не межузловая балансировка.

«Логическая сеть» выбирает Service + worker и показывает 11 этапов до процесса приложения; пошаговая трасса содержит DNS и обратный путь, подсветку портов/кабелей/ядра, IP/порты до и после NAT и управление слежением камеры. Кластерные связи отделены от сетевых кабелей и огибают ноды; при трассировке они приглушаются. JSON-пример: examples/proxmox-kubernetes.json.


## NodePort Cluster и routed CNI

В инструкции демо кнопка «Cluster · межузловой путь» обновляет текущую схему без замены ID нод, NIC и кабелей. Однократная резервная копия сохраняется как infra-lab-backup-before-cluster-policy; прежняя копия «До демо» остаётся нетронутой. ВМ с Pod раскрываются. Политика Local/Cluster и предпочтительный Pod выбираются у Service. Предпочтительный endpoint — детерминированный сценарий демонстрации, не алгоритм балансировщика Kubernetes.

Cluster: запрос клиента к worker-01:30080 направляется на готовый Pod worker-02. DNAT заменяет назначение на 10.244.2.10:80, iptables-модель MASQUERADE/SNAT заменяет источник на IP выходного интерфейса worker-01. В случае удалённого Pod это 10.10.0.21; при локальном backend — адрес cni0. Исходный порт сохраняется: коллизии NAT-портов не эмулируются. Ответ должен вернуться через тот же входной Node; отдельно отображаются обратный SNAT назначения и обратный DNAT источника.

Выбран routed CNI / host-gw без туннеля: Ubuntu хранит явные маршруты Pod CIDR via Node IP. Трафик идёт eth0 → virtio → vmbr0 → физический NIC → SW-LAN → NIC другого Proxmox → vmbr0 → virtio → eth0 удалённой Ubuntu → L3 к cni0 → veth → eth0 Pod. Виртуальное членство в кластере не создаёт сетевого пути. Отсутствие маршрута, обратного gateway, кабеля, VLAN или IP forwarding даёт отказ в трассе. Прямой обмен Pod ↔ Pod по этим маршрутам работает без NAT.

В свойствах Service нажмите «Отказать выбранному Pod», затем отправьте новый запрос: NotReady endpoint исключается, выбирается вторая готовая реплика. «Восстановить готовность Pod» возвращает readiness. Остановка контейнера или приложения также делает endpoint неготовым в учебной модели. NotReady сам по себе не останавливает процесс: прямой доступ к IP Pod остаётся возможным. Перенос уже установленного TCP-соединения при отказе не эмулируется. Реальная синхронизация EndpointSlice, интервалы health-check и автоматическое восстановление реплик scheduler не моделируются.

Архитектура: Node — родительская Ubuntu-ВМ целиком. Вложенная пунктирная рамка обозначает kubelet/runtime и управляемые Pod; собственного NIC, отдельной ОС или дополнительного namespace у этой группы нет. eth0, Linux-мост cni0, veth хостового конца, маршруты и правила kube-proxy находятся в ядре Ubuntu. Контейнеры одного Pod разделяют eth0/IP/порты. Containerd управляет контейнером Nginx; сам контейнер не является Docker Engine. Runtime явно подписан на контейнере. Мост cni0 относится к выбранному варианту CNI: другие реализации могут использовать overlay или eBPF и не обязаны иметь такой мост.

Подсветка CNI показывает логический L3-переход внутри Ubuntu, отдельно от кабелей. Карточка входного ядра для remote backend указывает next-hop, а cni0 относится к удалённому worker. Логическая сеть автоматически выбирает входной Node текущего запроса и показывает 13 этапов при remote Cluster. JSON-пример: examples/proxmox-kubernetes-cluster.json.

Основания модели: [Kubernetes network model](https://kubernetes.io/docs/concepts/services-networking/), [Service traffic policies](https://kubernetes.io/docs/reference/networking/virtual-ips/), [Source IP and Cluster/Local](https://kubernetes.io/docs/tasks/access-application-cluster/create-external-load-balancer/), [Container runtimes](https://kubernetes.io/docs/setup/production-environment/container-runtimes/).


## Отдельные kubelet, containerd и связи управления

У каждого Kubernetes-узла с runtime containerd отдельно показаны kubelet и daemon containerd. Они находятся в группе управления узлом рядом с Pod; контейнеры остаются вложенными в Pod, а приложения — в контейнер. В меню ОС можно создать standalone containerd / kubelet, в группе узла — создать их отдельно. У служб нет собственного NIC. У containerd задаются endpoint Unix socket / named pipe, namespace runtime и версия как описание.

Связи CTRL формируются по выбранному runtime в той же ОС: kubelet → containerd (CRI / gRPC через Unix socket) → контейнеры (управление жизненным циклом; shim / OCI runtime свёрнуты). Эти розовые стрелки с треугольным наконечником и подписями CTRL рисуются отдельным слоем. Они не записываются в массив сетевых кабелей, не потребляют интерфейсы, не участвуют в L1/L2/L3, NAT и прохождении HTTP. При сетевой трассировке слой приглушается. Тумблер «Управление» в тулбаре скрывает только CTRL; легенда объясняет обозначения. В свойствах службы перечислены входящие/исходящие связи и их назначение.

Старая схема обновляется идемпотентно: добавляются управляющие службы, сохраняются ID существующих нод, NIC, IP, кабелей и вложенность Pod/контейнеров. Исходный localStorage один раз резервируется как infra-lab-backup-before-runtime-control. Ручная прокладка кабелей остаётся в проекте, при изменении размеров нод применяются штатные проверки маршрута. Управляющие стрелки автоматически сохраняются через сущности/ссылки runtimeId, переживают импорт/экспорт и копирование. При сворачивании родителя внутренние стрелки скрываются, внешние привязываются к видимому контейнеру без создания фиктивных сетевых портов.

Удалённый daemon не появляется снова при загрузке: marker controlModel сохраняет намеренное удаление, ссылки очищаются. Удаление изображения службы не означает остановку работающих контейнеров, поэтому сетевые кабели не удаляются и HTTP не обрывается искусственно. Полноценный CRI lifecycle emulator не реализован. Документация протокола: [Kubernetes CRI](https://kubernetes.io/docs/concepts/containers/cri/).
